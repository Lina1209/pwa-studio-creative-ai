# Creative Asset Storage Architecture

Status: architecture and source audit only. No live database, bucket, policy, or provider state was changed.

## 1. Goal

Give every PWA Studio branch one safe, reusable asset library. An image created in the Image Studio should be reusable in a film; a music track should be attachable to a video project; a voice recording should be available to scenes and edits. Reuse should reference the same asset rather than silently creating duplicate uploads.

The asset shelf in Creative Control Center remains an honest empty-state UI until metadata and storage APIs are implemented and verified.

## 2. Repository source audit (branch snapshot)

Reviewed the current backend routes/services, Supabase storage migrations, storage setup guide, and read-only diagnostic SQL.

### What exists

- Supabase Auth is verified by the FastAPI backend; `get_current_user` derives the user UUID from a validated JWT.
- A server-only Supabase REST helper exists for service-role operations.
- Mini Cinema movie-project drafts have a browser `localStorage` copy and an authenticated cloud project-sync path to `public.projects` in `app.js`. This is project JSON persistence, not media-binary upload or a shared asset library. Guest drafts remain device-local. Cloud sync depends on the live table and owner-only RLS being correctly configured; production isolation and cross-device behavior still require verification.
- Migration sources define private buckets named `studio-media` and `studio-exports`, and a user-owned `public.projects` table.
- A read-only diagnostic script exists at `supabase/diagnostics/inspect_cloud_storage.sql`.

### What is not implemented or not verified

- No dedicated asset metadata table or asset CRUD service/routes were found in the reviewed backend.
- No backend upload, signed-download, asset-linking, or deletion lifecycle API was found.
- No verified cross-studio asset references exist yet.
- The live schema, migration ledger, bucket configuration, Storage policies, and grants have not been inspected in this audit. Source files are not proof of live state.

### Migration and policy conflict that blocks rollout

- `0002_storage_and_moderation.sql` configures both buckets. It sets `studio-media` to 250 MiB and `studio-exports` to 1 GiB, and creates policies that cover both buckets.
- `0005_cloud_projects_and_storage.sql` later configures `studio-media` to 100 MiB and recreates the same named Storage policies with conditions limited to `studio-media`.
- Because the policy names are shared, applying the later migration can replace the earlier combined-bucket policies. The export bucket may consequently lack the expected user policies.
- The repository also contains two different migration files named version `0005`. Do not rename, reorder, replay, or apply either file until the live migration ledger and actual policies are reconciled.

This is a source-level risk finding, not a claim about the current live Supabase state.

## 3. Target architecture

### 3.1 Private object storage

- All user assets and exports are private by default.
- Never expose service-role credentials or public bucket URLs to the browser.
- Object access is owner-scoped and checked on the server for every operation.
- Downloads use short-lived signed URLs or a backend-mediated stream after authorization.
- Object paths are generated by the server and begin with the authenticated owner's UUID. Never trust a client-supplied owner path.
- Separate original/source assets from rendered exports if lifecycle, size, or retention policies require it; bucket choice must follow the reconciled live configuration rather than assumptions.

### 3.2 Canonical asset metadata

Introduce a single canonical asset record (exact SQL schema is deferred until live-schema audit). It should represent at least:

- immutable asset ID and owner UUID;
- storage bucket and object key;
- media kind: image, video, audio, music, voice, document, or other approved type;
- verified MIME type, byte size, checksum, and optional media dimensions/duration;
- display name and safe metadata (never prompt text or private content by default);
- lifecycle state: pending, processing, ready, quarantined, deleting, deleted, or failed;
- source operation/branch and optional provider/job reference;
- created/updated timestamps and deletion/retention metadata.

Keep asset metadata separate from project content and from the credit/usage ledger. A project should reference an asset ID; it should not need to duplicate the asset binary or own its lifecycle.

### 3.3 Project and cross-studio relationships

Use explicit owner-scoped relationships between assets and projects/operations:

- One asset may be referenced by multiple projects and multiple studio branches owned by the same user.
- A project reference records its role (for example: poster, scene image, soundtrack, voiceover, source clip, export).
- Removing an asset from a project removes the relationship, not automatically the underlying asset.
- Deleting an asset requires a clear confirmation and a reference check; shared references must not become broken silently.
- Cross-user sharing is a separate future feature and must not be inferred from a copied asset ID.

### 3.4 Upload lifecycle

1. Authenticated client requests an upload intent with media kind, declared size, and MIME type.
2. Backend validates the user, limits, allowed media type, quota policy, and idempotency key.
3. Backend creates a pending metadata record and a server-generated object key.
4. Client uploads to the private bucket using a narrowly scoped, short-lived authorization mechanism.
5. Backend verifies object existence, actual size/type, checksum where available, and ownership.
6. Asset becomes ready only after verification. Failed or abandoned uploads are expired and cleaned up safely.

Do not trust browser-provided MIME type or size as final evidence. Enforce maximum sizes and allowed types on both the upload authorization and verification paths. Consider malware/content scanning and quarantine before enabling public sharing or downstream processing.

### 3.5 Reuse and idempotency

- Upload retries must not create multiple metadata rows for the same logical request.
- Use server-generated idempotency keys scoped to owner and operation.
- Reuse an existing ready asset by ID when attaching it to another project.
- Do not copy bytes between branches unless a provider or transformation genuinely requires a derivative.
- Derivatives are separate assets with a source-asset relationship and their own lifecycle.

### 3.6 Deletion and retention

- Soft-delete metadata first and prevent new references/downloads.
- Confirm whether an asset is referenced by active projects or jobs before removing the object.
- Use a retryable cleanup worker for object deletion; do not report deletion complete until storage confirms it.
- Keep minimal audit metadata where legally and operationally appropriate, without retaining user media unnecessarily.
- Define retention and account-deletion behavior before launch.

## 4. Security and privacy requirements

- Owner identity comes only from verified server authentication, never from request-body `user_id`.
- Every metadata query and relationship mutation is filtered by authenticated owner.
- Storage policies and backend checks must agree; neither is a substitute for the other.
- Service-role credentials remain backend-only.
- Signed URLs are short-lived and are not stored as permanent asset fields.
- Validate extension, MIME signature/content where practical, size, path, and media duration/dimensions.
- Rate-limit upload-intent and completion endpoints; cap concurrent uploads and total storage usage.
- Avoid logging signed URLs, access tokens, prompts, media contents, or sensitive metadata.
- Keep user assets private unless the owner explicitly initiates a separately designed sharing action.

## 5. API surface (proposed, not implemented)

A future versioned API may include:

- `POST /api/assets/upload-intents` — authorize one upload and create a pending record.
- `POST /api/assets/{asset_id}/complete` — verify the uploaded object and finalize metadata.
- `GET /api/assets` — list the authenticated user's assets with safe filters and pagination.
- `GET /api/assets/{asset_id}` — retrieve safe metadata.
- `POST /api/assets/{asset_id}/access` — issue a short-lived download/access URL after owner authorization.
- `POST /api/projects/{project_id}/assets` — attach an owned asset to an owned project with a role.
- `DELETE /api/projects/{project_id}/assets/{asset_id}` — remove a project relationship.
- `DELETE /api/assets/{asset_id}` — request safe asset deletion.

These are naming proposals only. Do not expose endpoints until schemas, authorization, storage behavior, and tests are implemented.

## 6. Delivery sequence and gates

### Phase 0 — reconcile existing state (current)

- Inspect the live Supabase migration ledger, table definitions, constraints, indexes, grants, RLS policies, buckets, bucket limits, MIME allowlists, and Storage policies.
- Compare live state with migrations 0002 and both 0005 files.
- Produce a migration reconciliation plan. Do not apply SQL during this phase.

### Phase 1 — metadata contract

- Agree on canonical asset and project-link data contracts.
- Design a forward-only migration with a new unique version after checking the live ledger.
- Review RLS, grants, indexes, ownership constraints, and deletion semantics.
- Test migration on a disposable Supabase/PostgreSQL environment first.

### Phase 2 — backend storage service

- Implement upload intents, completion verification, listing, access URLs, project linking, and deletion.
- Add unit tests for owner isolation, invalid paths, MIME/size mismatch, expired intents, idempotency, and storage failures.
- Add authenticated integration tests against a disposable environment.

### Phase 3 — first branch integration

- Connect Mini Movie Studio and Media Library to the same asset service.
- Preserve local drafts and provide an explicit, safe import/sync path.
- Render only verified ready assets in the asset shelf.

### Phase 4 — cross-studio reuse

- Connect Image, Music, Voice, Video, and Render branches incrementally.
- Reuse asset IDs and create explicit derivatives when needed.
- Add background cleanup, quota metering, and observability only after resource measurement is reliable.

## 7. Rollout boundaries

- No SQL migration is proposed or applied by this document.
- No live Storage policy or bucket setting is changed.
- No upload or provider call is triggered.
- No credit deduction, subscription, billing, or paid storage quota is activated.
- Do not populate the asset shelf with mock assets or claim cloud synchronization until end-to-end behavior is verified.


## 2.1 Historical cloud-project verification and current diagnostic coverage

The working roadmap records a manual live verification on 2026-11-21: `0005_cloud_projects_and_storage.sql` was applied to the connected Supabase project; `public.projects`, its owner policies, the private `studio-media` bucket, and a test project row were checked, and the test project remained visible after browser refresh. This is historical evidence for the project table and basic same-session persistence only. It does not establish current cross-device behavior, two-account isolation, complete migration history, or the current state of the export bucket and its policies.

The admin Supabase diagnostics endpoint performs read-only REST HEAD checks with a zero-row limit. The source review found that it checked profile, notification, messaging, and moderation tables but did not include the already-used `public.projects` table. The diagnostics table map now includes `projects` so an administrator can see whether the cloud-project REST resource is exposed without reading project rows. This is a connectivity/availability signal only: it does not inspect RLS correctness, bucket configuration, object policies, or project contents.

The asset rollout must therefore preserve the verified `projects` foundation and avoid re-running its historical migration. The remaining read-only live audit should focus on the exact project-table definition/policies, the private `studio-media` bucket, the uncertain `studio-exports` bucket/policies, and the migration ledger before any asset schema or upload API is introduced.


## 7. Clarification: project cloud sync is not asset storage

A source review of the current Mini Cinema implementation confirms a real cloud persistence path for movie-project records. The earlier statement that movie-project cloud synchronization was not connected is superseded by the current frontend source review.

The distinction is important:

- `public.projects` stores project records and serialized workflow/settings data.
- The per-account browser copy is a local fallback/cache.
- Guest drafts are stored locally and no automatic guest-to-account migration was found.
- No corresponding asset metadata API, upload-intent flow, media binary upload, shared asset listing, signed download, or cross-studio asset relationship service was found.

Therefore, the Mini Cinema project cloud-sync feature must be preserved and tested; it must not be mistaken for a completed Media Library or shared asset-storage system. Production RLS and cross-account isolation remain unverified.
